## Executive verdict

The repository is unusually serious about provenance. Its strongest features are:

- immutable raw data with SHA-256 manifests;
- explicit source/citation mapping;
- a shared object-matching implementation with synthetic and regression tests;
- editable SVG builders rather than manually assembled final figures;
- honest README caveats about one-field scope and unreproduced published model outputs;
- a pre-specified Figure 3 protocol that stores every prompt, reply, output and deviation.

However, the repository is **not yet a complete end-to-end reproducibility package**. The most important problems are:

1. two Figure 1 rerun scripts currently write to paths that are not the paths used by the figure/scoring code;
2. `make check` rebuilds figures from already committed derived source files and reruns only a subset of the processing steps, so it can pass while upstream outputs are stale;
3. Figure 1's claimed final check on a fresh image is currently another crop from the same field and substantially overlaps the development/reference region;
4. Figure 3 round 2 has a critical asymmetry: the generic optimisation agent receives the whole image, including the nominal held-out half, whereas the Box 1 agent receives only the left half;
5. the BioSR pixel-size documentation is internally inconsistent and must be reconciled before relying on the reported tubule widths;
6. several Figure 2 results are tuned or measured on one field and should remain explicitly illustrative rather than being presented as performance estimates.

The figures can support the paper's narrative after these issues are fixed or clearly disclosed. At present, the repository is strong as an auditable working record, but it overstates how much is regenerated by the default checks.

## Priority findings

### P0 — fix before submission or public release

#### P0.1 Figure 1 rerun scripts write to stale/non-canonical paths

Two scripts no longer update the files used by the current figure and score calculation:

- [`fig1/code/classical_seg.py`](../fig1/code/classical_seg.py) writes `panel_c_steps2_4/classical_labels.tif`, whereas [`fig1/code/f1_scores.py`](../fig1/code/f1_scores.py) reads `full_field_labels/threshold_labels.tif`.
- [`fig1/code/segment_bf_cellpose.py`](../fig1/code/segment_bf_cellpose.py) writes `panel_c_step3/BF_cellpose_sam_labels.tif`, whereas the current score and Figure 2 code read `full_field_labels/cellpose_sam_labels.tif`.

This means that rerunning either analysis script does not update the canonical derived label image used in the published scores. A stale output can therefore survive while the script appears to run successfully.

**Required fix**

- Define one canonical output path for each derived result.
- Update all producers and consumers to use it through a shared path function/configuration.
- Add a regression test that deletes the canonical generated file in a temporary working copy, runs the producer, and verifies that the expected file was recreated and used by the scorer.
- Remove or clearly archive obsolete duplicate paths.

#### P0.2 `make check` is not an end-to-end raw-data-to-figure check

[`tools/check_all.py`](../tools/check_all.py) copies each complete figure folder into a temporary directory. That copy already contains the committed derived PNGs, TIFFs and JSON files. The figure builders then redraw SVGs from those committed derivatives. This proves that the final builder is deterministic given the committed source data; it does **not** prove that all source data can be regenerated from `data/raw/`.

For Figure 2, the default check reruns:

- `errors.py`
- `score_perturb.py`
- `annot_agree.py`
- `bio_result.py`
- `al_intensity.py`
- `tubule_width.py`

It does not rerun several upstream producers, including:

- `norm_inputs.py`
- `cellpose_perturb.py`
- `postfilter.py`
- `al_roi.py`
- `al_gray.py`
- `image_generation.py`

SQUIRREL is also excluded unless `tools/check_all.py --with-squirrel` is used. The README currently says that `make check` reruns Figure 1 and Figure 2 scoring and rebuilds everything, which is too broad.

A second isolation issue is that temporary figure copies still import `common.paths` from the original repository root through `PYTHONPATH`. They therefore read the original repository's raw data, not a self-contained fresh copy.

**Required fix**

Create an explicit dependency graph:

```text
raw data -> derived analysis outputs -> scores -> figure assets -> SVG/PDF
```

Then provide either:

- `make check-fast`: verifies raw hashes, tests, committed derived outputs and builder determinism; and
- `make check-full`: starts from an empty generated directory and recreates all feasible derived outputs, scores and figures, including SQUIRREL in its pinned environment;

or one full release check that does this by default.

The full check should fail when an expected upstream file is missing; it should not begin from a copy containing that file.

#### P0.3 Figure 1c does not currently demonstrate a genuinely fresh-image check

The Figure 1 README already discloses that steps 2–4 come from one field and that the final-check crop overlaps the reference crop almost completely. The visual and legend nevertheless communicate a progression from reference data to a final check on fresh images.

That is a narrative mismatch: a spatially shifted crop from the same acquisition is not evidence of generalisation to a new field, repeat, day or imaging condition.

**Preferred fix**

Use the pending second annotated field for the final-check panel and score it without using it during method selection.

**Acceptable fallback**

Relabel the panel as an "additional region from the same field" and explicitly state that it checks local transfer only, not generalisation. Do not use the word "fresh" or "independent" for the current crop.

#### P0.4 Figure 3 optimisation conditions do not use the same image split

[`fig3/round2/make_scenarios.py`](../fig3/round2/make_scenarios.py) currently defines:

```python
FOLDER = {
    "generic": "image.tif <- {t}_image.tif",
    "box1": "image_left.tif <- {t}_image_left.tif; annotation_left.tif <- {t}_annotation_left.tif",
}
```

Thus, in the optimisation row:

- the generic agent sees the entire field, including the right half later called held out;
- the Box 1 agent sees only the left-half image and annotation.

This is not a clean held-out comparison. The generic agent can visually adapt to the right-half image even without its labels, whereas the Box 1 agent cannot. The two conditions also receive different spatial contexts and image sizes.

**Required fix**

Give both optimisation conditions the same left-half image. The Box 1 condition additionally receives the left-half annotation/reference objective. Freeze both resulting pipelines, apply them to the whole field, and score only the right half. Better still, optimise on one field and test on a second annotated field when available.

The strategy and legend should then describe the comparison accurately: it tests optimisation without versus with an external annotated objective; it does not isolate every individual Box 1 instruction.

#### P0.5 Objects crossing the Figure 3 left/right split are handled inconsistently

[`fig3/round2/make_assets.py`](../fig3/round2/make_assets.py) clears split-border objects only for the endothelial-cell task. Nuclei and cancer-cell annotations can be truncated at x = 512 and appear as partial objects in development or held-out scoring. [`fig3/scoring/tasks.py`](../fig3/scoring/tasks.py) similarly applies `clear_border` only to endothelial predictions/references.

Partial objects can distort IoU, area and object counts at the split boundary.

**Required fix**

Use one pre-specified split convention for all tasks, for example:

- remove every reference and prediction touching a buffer around the split from both halves; or
- split by complete annotated objects, with a fixed exclusion band.

Report the resulting reference counts per task after applying the convention, and unit-test boundary cases.

#### P0.6 Resolve and test the BioSR physical pixel size

[`fig2/code/tubule_width.py`](../fig2/code/tubule_width.py) uses 31.3 nm per pixel on the 2x super-resolved grid, while comments elsewhere describe the high-resolution pixel as 62.6 nm or use ambiguous wording. The BioSR raw/widefield sampling is 62.6 nm, while the 2x reconstructed grid is expected to be 31.3 nm; the code is likely correct, but the repository documentation is internally inconsistent.

Because every reported tubule width depends linearly on this value, a factor-of-two metadata error would produce a factor-of-two measurement error.

**Required fix**

- Derive the scale from source metadata or a checked data card rather than a bare constant.
- Store raw-grid and 2x-grid pixel sizes explicitly.
- Add a test that checks the image dimensions and expected 2x scale relationship.
- Correct the contradictory comments in `image_generation.py`, `fig1/README.md` and any figure data cards.

### P1 — major scientific or reproducibility issues

#### P1.1 Figure 1b must be visibly labelled illustrative

The prompts and replies in Figure 1b were composed for the schematic and are not recorded model outputs. This is disclosed in the repository, but the panel visually resembles empirical LLM results.

Add "illustrative examples" directly to the panel or legend. Figure 3 should be the empirical test of LLM behaviour.

#### P1.2 Figure 1c scores are one-field illustrations, not a model comparison

The threshold, generalist and custom model scores use one field. The custom StarDist prediction may also have been produced from a model whose relationship to this field's training data still needs confirmation. The panel should not imply that custom training generally outperforms generalist or classical approaches.

Add "one illustrative field" and confirm whether field 104 was excluded from custom-model training. If that cannot be established, state it.

#### P1.3 Figure 1 classification input and output are not a matched pair

The Figure 1 README says the classification gallery comes from other test images rather than the input tile shown. That visual pipeline can be read as though the shown input produced the shown output.

Use a matched input/output pair or label the output as an "example class gallery" rather than a direct result.

#### P1.4 Figure 2a includes reference-tuned choices

The post-filter threshold and the displayed alternatives were evaluated against the same manual annotation used to report F1. The resulting F1 = 0.92 is useful as a diagnostic demonstration, but it is not an unbiased performance estimate.

Label it as "tuned on this example" or select settings using separate development data and report performance on a new field. The same caution applies to choosing the best normalisation or scale from the displayed alternatives.

#### P1.5 Figure 2 super-resolution locations are not biological replicates

The reported 2,450 tubule-width locations come from one image. They are spatial samples, not independent biological replicates. The figure should say "2,450 sampled locations in one image" and should not attach inferential uncertainty or biological-generalisation claims to that number.

The location rule also conditions on the union of skeletons from the prediction and reference, while orientation is taken from the reference. This is defensible for an illustrative paired measurement but must be described because it is not a neutral, model-independent sample of all structures.

#### P1.6 The default installation command is likely incomplete

`environment/requirements.txt` pins `torch==2.14.1+cpu` and comments that it should be installed from the PyTorch CPU index, but the root README instructs users to run a single default-index command:

```bash
python3 -m pip install -r environment/requirements.txt
```

The `+cpu` build normally requires the specified alternate index. Split the environment into:

- base figure/scoring dependencies;
- optional Cellpose/PyTorch dependencies with an explicit installation command/index;
- NanoPyx/SQUIRREL environment.

Add a lockfile or container and test the exact documented commands in CI.

#### P1.7 Public release is blocked by unresolved provenance/licence items

`data/README.md` still asks to confirm:

- BioSR redistribution licence;
- annotator names, annotation tool and dates;
- denoising source/training/version details;
- TrackMate provenance and some pixel-size details.

Resolve these before making the repository public. The source table currently mixes data licences and method citations in one field; separate `data_licence`, `permission_status`, and `method_citation`.

#### P1.8 Duplicate scoring and conversion code remains

The repository has a tested shared matcher in `common/matching.py`, but legacy duplicate matchers remain in Figure 1 and Figure 2 code. `classical_seg.py` imports `fig1/code/compare_cancer_gt_lib.py`, not the shared implementation. `lines_to_cells` is also duplicated in multiple Figure 2/Figure 3 scripts.

Use one shared implementation and unit-test it. Duplicated scientific logic can drift silently.

#### P1.9 Greedy matching should be documented and tested more fully

`common/matching.py` performs greedy one-to-one matching in descending IoU order. It is deterministic and tested on basic cases, but it is not guaranteed to maximise the number or total IoU of matches for every overlap graph.

At IoU >= 0.5, ambiguous conflicts may be rare, so this is not necessarily wrong. Document the convention explicitly and add tests for:

- empty reference/prediction;
- exact threshold equality;
- tied IoUs;
- one prediction overlapping several references and vice versa;
- a constructed case where greedy and maximum-cardinality matching differ.

If the last case can alter reported numbers, use a maximum bipartite matching rule or justify retaining greedy matching for continuity.

#### P1.10 Several Figure 2 scripts tolerate stale or missing intermediates

Examples:

- `score_perturb.py` records a missing run as `None` and continues rather than failing.
- `annot_agree.py` silently omits the model when `cp_pecam.tif` is absent.
- `postfilter.py` only writes its canonical output when an argument is supplied, but the default repository check does not rerun it.
- `image_generation.py` and other source generators are not part of the default reproducibility path.

Production/release builds should fail loudly when a required panel input is absent.

#### P1.11 Correlation in artificial labelling is not calibration

`al_intensity.py` reports Pearson correlation between predicted and acquired per-object intensities. Correlation tests ranking/co-variation, not equality, calibration or preservation of ratios. The figure and legend should avoid implying quantitative equivalence from `r` alone.

If intensity fidelity is a claim, also report slope/intercept or a paired error/calibration plot, and state the separately stretched displays are for visualisation only.

#### P1.12 Error categories in `errors.py` are heuristic

The merge/split/missed/false categories use custom 50%-overlap rules. That is acceptable for an illustration, but they are not standard definitions and are distinct from the IoU matching rule used for F1.

Document them as heuristics in the figure README and add synthetic tests for representative merges and splits.

### P2 — robustness and maintainability

- `data/add_raw_files.py` does not verify that `--source` exists in `sources.csv`, allows duplicate role keys to overwrite silently, and can leave a partially updated repository if a later copy/write fails. Validate source keys and roles, sanitize prefixes, and stage changes atomically.
- Hard-coded pixel sizes, crop coordinates and one-row alignment corrections appear in several scripts. Move them to a checked per-dataset metadata file and validate image shapes before slicing.
- `al_roi.py` and `al_intensity.py` hard-code the pix2pix one-row shift without an alignment assertion.
- `al_gray.py` independently contrast-stretches predicted and acquired halves. This is acceptable for display, but the panel/legend should state that the display scaling is independent and cannot be used to compare intensity.
- `image_generation.py` states that a selected line profile is near the median/typical, but the script does not calculate or assert that selection criterion. Either implement and record the selection or remove the claim.
- Several docstrings refer to superseded panel letters (for example, `al_intensity.py` and `image_generation.py`). Correct them to reduce audit confusion.
- Add empty-result guards before medians/correlations/FWHM summaries so failure produces an informative error rather than NaNs or misleading output.
- Use SHA-256 rather than MD5 for generated-file comparisons for consistency with the raw-data manifest. MD5 is not a scientific correctness problem here, but one hash convention is clearer.

## Figure-specific narrative assessment

### Figure 1

**Narrative fit:** strong. The three panels map well to the manuscript: deep-learning uses, LLM delegation, and starting a project from the measurement/reference data.

**What weakens it:** panel b resembles recorded results although it is illustrative; panel c looks like a small benchmark and overstates independence of the final check; the classification pair is not matched.

**Recommendation:** keep the figure, but label illustrative components directly and replace the final-check crop with the pending second field. If no second field is available, remove the claim of fresh-image validation from the visual.

### Figure 2

**Narrative fit:** strong and more distinctive than a generic validation schematic. It directly supports the manuscript's main message: validation depends on what the output will be used to measure.

**What weakens it:** one-field tuning in panel a, correlation potentially being read as quantitative equivalence in artificial labelling, and 2,450 spatial samples potentially being read as independent replication in super-resolution.

**Recommendation:** keep all panels, but label the tuning and sampling scope. Resolve the physical-scale metadata before submission.

## Figure 3 round-2 plan

### What is strong

The plan contains many safeguards that should be retained:

- protocol, prompts and answer sheet frozen before collection;
- all runs retained and every run plotted;
- new session per scenario, memory/personalisation off;
- operator and subject roles separated;
- exact prompts, follow-up answers, code and edits stored;
- code run independently of in-app execution;
- descriptive reporting only, no inappropriate statistical claims for n = 3;
- scoring against authors' manual annotations with shared code;
- separate optimisation and final-evaluation data;
- fixed advice rubric with blinded duplicate scoring;
- willingness to change the manuscript if results contradict the intended story.

This is substantially better than an anecdotal prompt demonstration.

### Required design corrections before tagging the protocol

1. **Fix the optimisation input asymmetry** described in P0.4.
2. **Remove/exclude split-boundary objects consistently** for all three tasks.
3. **Use a second annotated field if available.** One left/right split in one acquisition tests spatial transfer within a field, not generalisation to another experiment. If a second field cannot be obtained, state this prominently and avoid broader language.
4. **Check split balance before runs.** Report object counts, size distributions and difficult-object prevalence in development and held-out regions. A single split can accidentally favour one condition.
5. **Do not claim the experiment isolates individual prompt rules.** Box 1 changes task information, model-domain information, code instructions and validation requests together. The result estimates the effect of the complete Box 1 prompt versus a minimal prompt.
6. **Describe the advice rubric as adherence to the paper's recommended practices**, not an unbiased universal measure of advice quality; several items are structurally prompted by Box 1.
7. **Make `score_round2.py` robust to missing/invalid outputs.** It currently assumes valid `reply.json` and `stated_count.txt`. Invalid JSON, missing files, non-integer counts, ranges and malformed polygons should produce an explicit failure record rather than crash the scorer.
8. **Audit polygon rasterisation.** Later polygons currently overwrite earlier polygons silently. Record overlaps, empty/out-of-bounds polygons and mismatches between stated count and number of valid outlines.
9. **Derive manual whole-field counts from the reference label images** instead of hard-coding them in `score_round2.py`.
10. **Clarify direct-answer evaluation.** Generic counts are whole-field, while outline F1 is held-out-half. Report stated count, valid outline count, whole-field count error and held-out outline F1 separately; do not collapse them into one score.
11. **Increase transcript auditing.** Ten per cent is light for 162 AI-operated runs. At minimum, automatically validate metadata and attachments for every run, manually inspect every deviation/failure/follow-up exchange, and inspect a larger pre-specified random sample.
12. **Create the `fig3-round2-protocol` tag before any run.** It was not present at the time of this audit.
13. **Record interface limitations honestly.** Free-tier default models and app behaviour can change during collection. The exact displayed model string, interface, date, web state, file conversion and code-execution mode are essential.
14. **Review workload against drift risk.** The full 162-run design is defensible for an illustrative figure, but it is operationally heavy. If it cannot be completed within the intended short window, reduce the design before starting rather than collecting a partially time-confounded set.

### Important interpretation limits

- Three replicates from one field cannot establish general model superiority.
- Generic versus Box 1 is a comparison of two complete user requests, not a causal decomposition of prompt elements.
- Agent runs with annotations test optimisation with an external objective; they do not test every benefit of Box 1.
- Direct-answer prompts compare a final number with a request for inspectable outlines and a number; this tests inspectability as well as prompting detail.
- Chat-app runs and API/sub-agent runs are not equivalent and should be shown/labelled separately if both are used.

## Bottom line

The repository already embodies the central message of the paper better than most figure repositories: outputs are tied to reference data, assumptions are explicit, and limitations are documented. The remaining problems are not cosmetic. They concern stale generated files, an incomplete definition of "rebuild", one misleading independence claim, and a confounded Figure 3 held-out design. Fixing those points would make the package credible as both a manuscript companion and an example of the practices the paper recommends.
